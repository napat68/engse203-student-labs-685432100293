# DATA_MODEL.md — การออกแบบฐานข้อมูล Campus Service Request

## 1. ภาพรวม

ระบบ Campus Service Request แบ่งข้อมูลออกเป็น 2 ตาราง ได้แก่ `users` สำหรับจัดเก็บข้อมูลผู้ใช้งาน และ `requests` สำหรับจัดเก็บข้อมูลคำร้อง โดยเชื่อมโยงกันผ่าน `requester_id`

```text
users
────────────────────────
PK  id
    name
    department
    email
         │
         │ 1
         │
         │ N
         ▼
requests
────────────────────────
PK  id
FK  requester_id
    request_type
    location
    details
    priority
    status
    created_at
```

ความสัมพันธ์ระหว่าง `users` และ `requests` เป็นแบบ **One-to-Many (1:N)** กล่าวคือ ผู้ใช้งาน 1 คนสามารถสร้างคำร้องได้หลายรายการ แต่คำร้องแต่ละรายการจะเป็นของผู้ใช้งานเพียง 1 คน โดย `requests.requester_id` เป็น Foreign Key ที่อ้างอิงไปยัง `users.id`

## 2. ทำไมต้องแยกเป็น 2 ตาราง

ใน Week 06–07 ข้อมูลชื่อผู้แจ้ง เช่น `requesterName` ถูกจัดเก็บเป็นข้อความอยู่ภายในคำร้องแต่ละรายการโดยตรง วิธีดังกล่าวสามารถใช้งานได้ แต่เมื่อมีข้อมูลจำนวนมากจะทำให้เกิดปัญหาหลายประการ

**1. ลดข้อมูลซ้ำซ้อน (Data Duplication)**  
หากผู้ใช้งานคนเดิมส่งคำร้องหลายครั้ง ชื่อและข้อมูลของผู้ใช้งานจะถูกบันทึกซ้ำในทุกคำร้อง เช่น สมชายมีคำร้อง 10 รายการ ก็อาจต้องเก็บชื่อสมชายซ้ำถึง 10 ครั้ง การแยกข้อมูลผู้ใช้งานไว้ในตาราง `users` ทำให้เก็บข้อมูลผู้ใช้เพียงครั้งเดียว แล้วใช้ `requester_id` เชื่อมโยงจากคำร้องแทน

**2. ลดปัญหาในการแก้ไขข้อมูล (Update Anomaly)**  
หากสมชายเปลี่ยนชื่อ และชื่อถูกเก็บอยู่ในคำร้องทุกแถว จะต้องค้นหาและแก้ไขทุกคำร้องของสมชาย หากแก้ไม่ครบจะทำให้ข้อมูลของผู้ใช้คนเดียวกันไม่ตรงกัน แต่เมื่อแยกตารางแล้วสามารถแก้ชื่อที่ `users` เพียงจุดเดียว คำร้องทั้งหมดที่เชื่อมกับ `user` คนนั้นก็ยังอ้างอิงข้อมูลเดียวกัน

**3. ลดความผิดพลาดจากการพิมพ์ข้อมูล**  
การกรอกชื่อผู้แจ้งซ้ำทุกครั้งอาจเกิดการสะกดต่างกัน เช่น มีช่องว่างเกินหรือพิมพ์ชื่อผิด ทำให้ระบบเข้าใจว่าเป็นคนละคน การใช้ `requester_id` ช่วยให้แต่ละคำร้องอ้างอิงผู้ใช้งานที่มีอยู่จริง

**4. รองรับการขยายระบบในอนาคต (Extensibility)**  
หากภายหลังต้องเพิ่มข้อมูลผู้ใช้งาน เช่น เบอร์โทรศัพท์ ตำแหน่ง หรือข้อมูลอื่น สามารถเพิ่มในตาราง `users` ได้โดยไม่จำเป็นต้องเพิ่มข้อมูลเหล่านั้นซ้ำในทุกคำร้อง

ดังนั้นการแยก `users` และ `requests` จึงช่วยลดความซ้ำซ้อน รักษาความถูกต้องของข้อมูล และทำให้โครงสร้างฐานข้อมูลรองรับการพัฒนาระบบในอนาคตได้ง่ายขึ้น

## 3. รายละเอียดตาราง

### ตาราง `users`

| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด | เหตุผล |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY, AUTOINCREMENT | ใช้เป็นรหัสภายในสำหรับระบุผู้ใช้แต่ละคนและสามารถเพิ่มค่าอัตโนมัติ |
| `name` | TEXT | NOT NULL | ผู้ใช้งานทุกคนต้องมีชื่อ |
| `department` | TEXT | NOT NULL | ใช้ระบุหน่วยงานหรือภาควิชา และสามารถใช้ค้นหาหรือกรองข้อมูลได้ |
| `email` | TEXT | NOT NULL, UNIQUE | ผู้ใช้ต้องมีอีเมลและไม่ควรมีบัญชีที่ใช้อีเมลซ้ำกัน |

### ตาราง `requests`

| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด | เหตุผล |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY | รองรับรหัสคำร้องในรูปแบบ `REQ-001` ซึ่งประกอบด้วยตัวอักษรและตัวเลข |
| `requester_id` | INTEGER | NOT NULL, FOREIGN KEY | ใช้เชื่อมคำร้องกับ `users.id` และป้องกันคำร้องที่อ้างอิงผู้ใช้ที่ไม่มีอยู่จริง |
| `request_type` | TEXT | NOT NULL, CHECK | จำกัดประเภทคำร้องให้เป็นค่าที่ระบบกำหนด |
| `location` | TEXT | NOT NULL | ทุกคำร้องต้องระบุสถานที่ที่เกี่ยวข้อง |
| `details` | TEXT | NOT NULL | ใช้เก็บรายละเอียดของปัญหาหรือความต้องการ |
| `priority` | TEXT | DEFAULT `'normal'`, CHECK | กำหนดระดับความสำคัญและป้องกันค่าที่ระบบไม่รองรับ |
| `status` | TEXT | DEFAULT `'pending'`, CHECK | ใช้ติดตามสถานะของคำร้องและจำกัดค่าให้ตรงกับสถานะที่ระบบรองรับ |
| `created_at` | TEXT | DEFAULT เวลาปัจจุบัน | บันทึกเวลาที่สร้างคำร้องเพื่อใช้ในการเรียงลำดับและตรวจสอบย้อนหลัง |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

### ทำไม `users.id` และ `requests.id` จึงใช้ชนิดข้อมูลต่างกัน

`users.id` ใช้ชนิด `INTEGER` และ `AUTOINCREMENT` เพราะเป็นรหัสภายในของฐานข้อมูล ไม่จำเป็นต้องมีรูปแบบสำหรับแสดงต่อผู้ใช้งาน และสามารถให้ SQLite สร้างหมายเลขต่อเนื่องให้อัตโนมัติได้

ส่วน `requests.id` ใช้ชนิด `TEXT` เนื่องจากรหัสคำร้องถูกกำหนดให้อยู่ในรูปแบบ เช่น `REQ-001`, `REQ-002` ซึ่งมีทั้งตัวอักษรและตัวเลข จึงไม่เหมาะกับชนิด `INTEGER`

### ทำไมต้องมี CHECK Constraint ทั้งที่ API ตรวจข้อมูลอยู่แล้ว

แม้ API จะมี Validation สำหรับตรวจสอบข้อมูลก่อนบันทึก แต่ฐานข้อมูลไม่ควรพึ่งพา API เพียงชั้นเดียว เพราะข้อมูลอาจถูกเพิ่มหรือแก้ไขจากช่องทางอื่น เช่น SQL โดยตรง หรือโปรแกรมอื่นในอนาคต

การกำหนด `CHECK` Constraint จึงเป็นการป้องกันข้อมูลผิดพลาดในระดับฐานข้อมูล เช่น ไม่อนุญาตให้ `status` มีค่าอื่นนอกจาก `pending`, `in-progress` หรือ `completed` ทำให้ฐานข้อมูลสามารถรักษาความถูกต้องของข้อมูลได้ แม้ว่าข้อมูลจะไม่ได้ผ่าน API ก็ตาม

## 5. ตัวอย่างการใช้ JOIN

ตัวอย่างการดึงข้อมูลคำร้องพร้อมชื่อผู้แจ้งจาก 2 ตาราง

```sql
SELECT
    r.id,
    u.name AS requesterName,
    r.request_type,
    r.location,
    r.priority,
    r.status
FROM requests AS r
JOIN users AS u
    ON r.requester_id = u.id
ORDER BY r.id;
```

ตัวอย่างผลลัพธ์

| id | requesterName | request_type | location | priority | status |
|---|---|---|---|---|---|
| REQ-001 | สมชาย ใจดี | แจ้งซ่อม | ห้องปฏิบัติการ 301 | urgent | pending |
| REQ-002 | สุภาวดี รักเรียน | บริการบัญชีผู้ใช้ | อาคารวิศวกรรม | normal | in-progress |
| REQ-003 | ธนกฤต ตั้งใจ | ขอใช้อุปกรณ์ | ห้องประชุม 2 | normal | completed |
| REQ-004 | สมชาย ใจดี | แจ้งซ่อม | ห้องปฏิบัติการ 302 | urgent | pending |
| REQ-005 | ปรียา ขยันยิ่ง | อื่น ๆ | ห้องสมุด ชั้น 2 | normal | pending |

การ JOIN ทำให้สามารถนำข้อมูลจาก `requests` และ `users` มารวมกันได้ โดยไม่จำเป็นต้องเก็บชื่อผู้แจ้งซ้ำไว้ในทุกแถวของตาราง `requests`

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

ใน Week 07 API ส่งข้อมูลให้ React ในรูปแบบที่มีข้อมูลคำร้องและ `requesterName` พร้อมใช้งาน ทำให้ Frontend สามารถนำชื่อผู้แจ้งไปแสดงผลได้ทันที

เมื่อเปลี่ยนมาใช้ฐานข้อมูลเชิงสัมพันธ์ใน Week 09 จะเห็นว่า `requesterName` ไม่จำเป็นต้องถูกเก็บซ้ำในตาราง `requests` เพราะสามารถเก็บข้อมูลผู้แจ้งไว้ใน `users` และใช้ `requester_id` เชื่อมโยงกัน จากนั้นใช้ `JOIN` เพื่อสร้างผลลัพธ์ที่มี `requesterName` ได้

ดังนั้นใน Week 10 ฝั่ง Backend สามารถใช้ SQL JOIN เพื่อดึงข้อมูลจากฐานข้อมูล แล้วจัดรูปแบบผลลัพธ์ให้มีโครงสร้างใกล้เคียงกับข้อมูลที่ API เคยส่งให้ React ใน Week 07 ได้ วิธีนี้ช่วยให้ Frontend ใช้งานข้อมูลได้สะดวกเหมือนเดิม ขณะที่ฐานข้อมูลมีโครงสร้างที่เป็นระบบและลดความซ้ำซ้อนของข้อมูล
