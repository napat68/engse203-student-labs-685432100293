## BUG #0 · ตรวจสอบความยาวรายละเอียดผิดที่ค่าขอบ 10 ตัวอักษร

- **อาการ:** ระบบปฏิเสธรายละเอียดที่มีความยาว 10 ตัวอักษรพอดี ทั้งที่ข้อกำหนดระบุว่าต้องมีอย่างน้อย 10 ตัวอักษร
- **วิธีทำซ้ำ:** ส่งข้อมูลคำร้องที่ถูกต้องทุกช่อง โดยกำหนด `details: '1234567890'` แล้วเรียก `validateRequestInput()` พบว่าระบบส่งข้อความ Error กลับมา
- **เครื่องมือ:** Unit Test ด้วย Vitest และ Boundary Value Analysis ทดสอบความยาว 9 และ 10 ตัวอักษร
- **สาเหตุ (ไฟล์:บรรทัด):** `api/src/validators/requestValidator.js` ภายในฟังก์ชัน `validateRequestInput()` ใช้เงื่อนไข `readText(input.details).length <= MIN_DETAILS` ทำให้ค่า 10 ถูกปฏิเสธ
- **วิธีแก้:** เปลี่ยนเครื่องหมาย `<=` เป็น `<` เพื่อให้รายละเอียดที่มีความยาวตั้งแต่ 10 ตัวอักษรขึ้นไปผ่านการตรวจสอบ
- **test ที่กัน:** `api/tests/unit/requestValidator.test.js` — `10 ตัวอักษร → ผ่าน (ตรงขอบพอดี)` โดย Test ล้มเหลวก่อนแก้ไข และผ่านหลังแก้ไข ผลทดสอบรวม 12/12 ผ่านทั้งหมด

## BUG #1 · ลบคำร้องแล้วเพิ่มใหม่ ได้ 500

- **อาการ:** เมื่อลบคำร้อง `REQ-002` แล้วเพิ่มคำร้องใหม่ ระบบตอบ HTTP 500 แทน HTTP 201
- **วิธีทำซ้ำ:** ส่ง `DELETE /api/requests/REQ-002` จากนั้นส่ง `POST /api/requests` ด้วยข้อมูลที่ถูกต้อง พบว่า API ตอบ 500
- **เครื่องมือ:** ใช้ Vitest และ Supertest เขียน Integration Test เพื่อจำลองการลบและเพิ่มคำร้อง พร้อมตรวจสอบผลการทดสอบ
- **สาเหตุ (ไฟล์:บรรทัด):** `api/src/services/requestService.js` ในฟังก์ชัน `nextId()` ใช้ `COUNT(*) + 1` สร้างรหัสใหม่ ทำให้เกิดรหัสซ้ำกับคำร้องที่ยังอยู่ในฐานข้อมูล
- **วิธีแก้:** เปลี่ยนเป็น SQL `MAX(CAST(SUBSTR(id, 5) AS INTEGER))` เพื่อหาหมายเลขสูงสุด แล้วบวก 1 สำหรับสร้างรหัสใหม่ที่ไม่ซ้ำ
- **Test ที่ป้องกัน:** `api/tests/integration/requests.api.test.js` — `ลบ REQ-002 แล้ว POST ใหม่ → ต้องสร้างรหัสไม่ซ้ำและตอบ 201` โดยก่อนแก้ไข Test ล้มเหลว (500) และหลังแก้ไข Test ผ่าน (201 พร้อมรหัส REQ-006)

## BUG #2 · Dashboard แสดงจำนวนกำลังดำเนินการเป็น 0

- **อาการ:** Dashboard แสดงจำนวนคำร้องที่กำลังดำเนินการเป็น 0 ทั้งที่มีคำร้องสถานะ `in-progress` อยู่จริง
- **วิธีทำซ้ำ:** ส่งข้อมูลคำร้องที่มีสถานะ `in-progress` จำนวน 2 รายการให้ฟังก์ชัน `summarizeRequests()` พบว่าผลลัพธ์ `inProgress` เท่ากับ 0 แทนที่จะเป็น 2
- **เครื่องมือ:** ใช้ Vitest เขียน Unit Test จำลองข้อมูลสถานะที่ API ส่งมา และตรวจสอบผลการนับจำนวนคำร้อง
- **สาเหตุ (ไฟล์:บรรทัด):** `frontend/src/utils/requestSummary.js` ในฟังก์ชัน `summarizeRequests()` ใช้ `count('in progress')` ซึ่งไม่ตรงกับค่า `in-progress` ที่ API ส่งมา
- **วิธีแก้:** เปลี่ยน `count('in progress')` เป็น `count('in-progress')` เพื่อให้การเปรียบเทียบสถานะถูกต้อง
- **Test ที่ป้องกัน:** `frontend/src/utils/requestSummary.test.js` — `BUG #2 — นับสถานะ in-progress จาก API ได้ถูกต้อง` โดยก่อนแก้ไข Test ล้มเหลว (`inProgress: 0`) และหลังแก้ไข Test ผ่าน (`inProgress: 2`)

## BUG #3 · เปลี่ยนสถานะคำร้องที่ไม่มีอยู่ ได้ 500

- **อาการ:** เมื่อเปลี่ยนสถานะคำร้องที่ไม่มีอยู่ เช่น `REQ-999` ระบบตอบ HTTP 500 แทนที่จะตอบ HTTP 404
- **วิธีทำซ้ำ:** ส่งคำขอ `PUT /api/requests/REQ-999` พร้อมข้อมูล `{"status":"completed"}` พบว่า API ตอบ 500
- **เครื่องมือ:** วิเคราะห์ Stack Trace และใช้ Integration Test ด้วย Vitest + Supertest เพื่อทำซ้ำข้อผิดพลาด
- **สาเหตุ (ไฟล์:บรรทัด):** `api/src/controllers/requestController.js` ในฟังก์ชัน `updateRequestStatus()` เรียก `updated.id` ก่อนตรวจสอบว่า `updated` เป็น `null` ทำให้เกิด `TypeError`
- **วิธีแก้:** ย้าย `console.log()` ไปไว้หลังเงื่อนไข `if (!updated)` เพื่อให้ระบบตรวจสอบคำร้องที่ไม่มีอยู่และตอบ HTTP 404 ก่อนใช้งานข้อมูล
- **test ที่กัน:** `api/tests/integration/requests.api.test.js` — `เปลี่ยนสถานะ REQ-999 → ต้องตอบ 404 ไม่ใช่ 500` โดย Test ล้มเหลวก่อนแก้ไข (500 แทน 404) และผ่านหลังแก้ไข
